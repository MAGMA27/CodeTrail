# 项目理解产品目标规范

状态：目标规范。本文定义产品目标和未来验收标准，不代表当前实现状态或已有验收结论。

## 产品定位

CodeTrail 是帮助人理解和修改 AI 生成代码的项目理解工作台。它帮助用户从项目全貌进入具体功能，沿代码关系核对源码，再把问题、解释和证据保存在项目会话中。

产品必须让用户能回答四个问题：

1. **职责是什么？** 项目的主要部分分别负责什么，边界在哪里？
2. **功能怎么工作？** 从用户动作、API 或 CLI 入口看，输入如何处理，状态存在哪里，结果如何产生？
3. **修改会影响什么？** 哪些引用、被引用和调用关系已确认，哪些影响仍未知？
4. **源码依据是什么？** 每个结论能否回到对应固定版本的源码证据？

## 用户旅程与工作区

核心旅程是：**路径导入 → 项目整体 → 功能探索 → 关系追踪 → 项目会话 → 核对源码与结论**。用户可以从项目或功能中的真实入口开始，也可以从一个待理解的问题开始；进入下一步时，项目、固定索引、当前功能和已选证据上下文应连续保留。

工作区围绕三个空间组织：

- **项目总览**：查看项目版本、职责容器、主要模块、依赖关系和覆盖边界。
- **功能探索**：从动作、API 或 CLI 入口查看有证据的功能旅程，并继续追踪关系。
- **项目会话**：保存用户问题、代码理解或 Issue 调查结果、证据和所用固定版本。

源码图、报告和上下文之间可以来回切换，返回后保留当前项目、索引、会话、选中位置和必要的视图状态。使用渐进式聚合，从职责容器进入模块、符号和源码，不要求首屏铺开全图；容器与依赖边帮助定位，箭头表示真实的 `source → target` 关系。依赖或调用可达不等于数据流，也不等于已确认的修改影响。

技术细节和索引诊断按需展开；未知应在相关入口、步骤或关系旁提示，避免让用户先读完整技术报告。第三方依赖的内部实现不作为本阶段的深入解释目标，但依赖边界和外部调用应可见。项目内部的别名、命名导入和唯一可确认的方法关系属于核心理解能力。

## 六项核心能力

| 能力 | 目标行为 |
| --- | --- |
| 项目版本与新鲜度 | 显示当前固定索引及源码版本；源代码变化后检查新鲜度，并由用户显式更新。更新产生新快照，旧会话、报告和证据仍指向原快照；界面能区分它们。 |
| 无 manifest 的职责解释 | 没有预写职责 manifest 时，仍能根据源码和关系给出有证据的职责说明；无法归属的部分显示未知或未覆盖，解释结果与静态分组分开。 |
| 从入口理解功能 | 从真实界面动作、API 或 CLI 入口说明输入、处理步骤、状态/存储、返回结果、分支及断点。多个请求分别列出；未连接到服务端的动作仍可解释，且明确标记连接边界。 |
| 双向引用与继续追踪 | 对符号和文件都能查看引用谁、被谁引用，并沿返回结果继续查询或打开同一快照的源码。保留真实边方向、证据位置和查询范围。 |
| 代码理解与 Issue 调查 | 两者是不同的用户意图和报告类型。理解回答代码如何工作；Issue 调查围绕具体缺陷和证据形成结论。理解结果不得伪装成缺陷候选或影响断言。 |
| HTTP/MCP 共享规则与持久结果 | HTTP、MCP 与工作台使用同一项目归属、快照、证据校验、权限和预算规则。工作台展示执行进度、公开工具结果和结论，外部 Agent 产生的持久结果可在网页实时查看并在刷新后恢复；读取历史不隐式重新生成。 |

## 证据与解释规则

界面和报告必须分别呈现以下状态，不能相互替代：

- **静态事实**：由固定快照中的源码和确定性规则直接支持，例如符号、导入和可解析调用。
- **模型解释/推断**：由 Agent 汇总或推断的说明，单独标识其来源，并附上支持它的源码证据；不能写回为静态边。
- **未知**：分析尝试过，但因动态行为、歧义或解析限制无法确认。
- **未覆盖**：没有检查、超出预算/返回范围，或当前能力不支持。未覆盖不能表达为“没有关系”。

每个事实性结论都应能追溯到同一 `project_id/index_id` 下的源码路径、位置及证据身份。HTTP method/path 形状可关联入口，但不是静态调用边；静态调用路径也不能声称运行时数据流。失败、截断和 unresolved 应作为可观察结果保留。

Agent 负责检索、调查和撰写有证据的解释；程序负责版本身份、证据解析、项目归属、权限、预算和持久化。无法回答时，系统保留断点及其原因，不用模型补成确定事实。技术详情可折叠，但用户需要时能核对来源与边界。

消息保存与执行分开，调用模型须显式触发并说明源码发送范围。MCP 调用方 Agent 可以承担解释与调查，服务端负责校验和保存其结果；不得为读取或提交结果隐式再调用服务端模型。网页不能将保存消息或复制任务显示成已启动 Codex。只展示公开事件、工具结果和证据，不展示隐藏思维链。

## 实施顺序

以下顺序是目标落地次序，不表示各阶段已完成。先让一个真实功能形成端到端闭环，再扩大功能和语言覆盖。

1. **G1：直接理解代码**：提供显式的理解入口，区分 Issue 调查，复用 Session、固定快照和有界证据流程。
2. **G2：通用功能旅程**：覆盖多请求动作、本地状态动作、可确认的结果，以及需要保留的断点。
3. **G3：关键代码关系**：补齐有界的文件级双向 imports、内部路径别名和唯一可确认的本地对象/方法调用；歧义时保留未知。
4. **G4：职责地图**：在无 manifest 项目上提供带源码映射的职责说明，并允许按职责、模块、符号渐进展开。
5. **G5：理解验收**：用一个非 CodeTrail 项目贯穿职责、真实功能、关系追踪、源码核对和版本更新后的旧会话辨识。

## 验收标准

验收样本为普通 Python、TypeScript 或 TSX 非 CodeTrail 项目，不预先编写职责 manifest。样本应至少包含一个可识别入口、内部引用关系、状态或存储位置，以及可观察的项目版本变化。不同语言使用当前明确支持的解析范围；本标准不承诺任意语言或框架。

| 检查面 | 可观察的通过条件 |
| --- | --- |
| 项目与快照 | 导入后可识别固定版本；源码变化能被发现但不会静默改写快照；显式更新后新旧索引可区分，已有 Session/报告仍绑定旧索引。 |
| 职责与边界 | 不提供 manifest 仍能查看有源码依据的主要职责；无法说明的模块、外部依赖和未覆盖范围有明确标记。 |
| 功能闭环 | 从真实动作或 API/CLI 入口追到输入、处理、状态/存储、结果、分支与断点；每个结论可打开同快照证据，并能区分静态事实、模型解释、未知和未覆盖。 |
| 关系追踪 | 能对符号和文件查看正反向引用，并从结果继续追踪或打开源码；关系方向真实，箭头不被解释为数据流或确定影响。 |
| 会话与结果 | 用户能发起并保存代码理解，也能辨别它与 Issue 调查的区别；执行中可见公开进度与失败状态；问题、结果、证据、分析类型和快照身份可恢复，历史读取不改变原结果。 |
| 接口一致性 | 对同一项目与快照，经 HTTP、MCP 和工作台执行的领域操作遵循相同归属、证据、权限、预算和持久化规则。 |

通过标准要求用户能够说明：该功能接收什么、关键处理与状态在哪里、结果如何产生；修改时能指出已有证据确认的调用者，并说清哪些环节仍无法确定。记录实际使用的样本、版本、操作和证据；未执行的检查保持未验证，不能由本规范本身推定通过。

## 范围与现有设计

MVP 面向单用户，工作区可切换多个独立项目，每个项目对应一个仓库，每次分析绑定一个只读固定快照。它不承诺任意语言/框架覆盖、执行仓库代码、运行时观测或全程序数据流证明，也不要求首轮深入解释第三方依赖内部实现。

产品目标不指定 Redis、Postgres、队列或其他基础设施。现有共享决策和技术提案继续按各自状态生效；本规范不将 proposed 决策改成已实施，也不否定它们。若具体技术决策与本目标发生范围冲突，应显式更新对应决策后再实施。相关设计见[项目工作区决策](../decisions/2026-09-11-project-workspace.md)和[项目与会话决策](../decisions/2026-09-11-project-session-workspace.md)。

界面布局、交互和视觉验收见[工作区 UI 规范](workspace-ui-spec.md)；现有验收证据及其历史状态见[MVP 验收清单](../mvp-acceptance.md)。两者不替代本文件定义的产品目标，也不因新增目标规范而改变既有状态。
