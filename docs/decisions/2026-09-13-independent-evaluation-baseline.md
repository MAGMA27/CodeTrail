# 决策：独立评测集与离线关键词基线

Status: implemented

## 问题

已有 `fixtures/` 能证明协议和边界，但不能衡量 Issue 定位质量，也不能作为真实模型比较的独立输入。P4-E1 需要在不执行被分析代码、不访问网络或真实模型的前提下，建立可复现的排序和证据合法性基线，并隔离评分答案，避免把开发样本输出反推成评测成绩。

## 决定

新增版本化 `evals/` 子系统，首批固定六个自有 Python 案例，校准/留出各三例；四例为至少三类缺陷的可定位案例，两例为本地证据不足或外部因素案例。每例源码仅从显式 `source/` 子目录建快照，Issue 独立保存，修复参考和评分标注放在 `annotations/`，不进入索引、关键词检索或工具可读源码根目录。

基线复用现有 SQLite/FTS5 服务，只把 Issue 标题和正文按 `unicode-word-v1` 分词，固定去重、关键词数、每词结果上限、候选聚合排序和 evidence 预算；不读取 `mentioned_paths`，不使用 gold 调整查询。检索完成后才由评分器计算 file/symbol/location Hit@1/3、证据合法率、证据不足案例的基线无候选/误报率、失败、耗时、调用和实际用量，并生成 JSON/Markdown 报告。后续 real Run 只能导入同一结果边界，不在本步运行付费模型。

## 替代方案

- 直接复用 `timeout-demo`：会把开发校准样本和评测样本混在一起，不能提供独立留出集，因此不采用。
- 让关键词基线读取预期位置或用答案调词：会把评分答案泄露到检索排序，无法作为可审查基线，因此不采用。
- 引入训练平台、队列、多 Agent 或新数据库：与离线小规模排序基线的边界不匹配，增加状态和运维面，因此不采用。
- 先运行真实供应商再定义评分：会把模型结果混入评测设计并产生费用；先冻结数据、格式和基线，再由 P4-E2 在相同输入上比较。

## 验收与证据

实现入口为 [evals README](../../evals/README.md)、[evals pipeline](../../evals/pipeline.py) 和 [评测子系统说明](../subsystems/evals.md)。本轮验收命令及结果补充在交付时同步到本记录和本地进度：

- `pnpm evals:validate` 校验六例、源码集合、hash、划分和标注隔离。
- `pnpm evals:test` 覆盖评分边界、失败/分母、预算、同名/跨快照和连续运行一致性。
- `pnpm evals:baseline` 在无网络/密钥条件下生成 `evals/results/p4-e1-v1/baseline-all.json` 与 `.md`。
- `pnpm docs:check`、`pnpm docs:check:local` 和必要的后端回归检查通过；本轮未修改共享产品契约。

实际报告必须给出逐例 Issue hash、snapshot hash、候选证据、失败原因和分子/分母；耗时、运行标识与工作树状态标为运行元数据。当前报告只证明关键词排序基线，不声称真实模型质量。

## 后果

评测输入、评分答案和开发 fixture 有明确边界，后续模型比较可以复用冻结数据和评分器；同时六例合成数据、固定词法和 FTS5 排序的外部有效性有限。基线对两个证据不足案例可能产生本地相关候选，需把误报率作为结果而非隐藏。修改冻结源码必须提升数据版本并重新生成 manifest/报告。运行临时 SQLite 留在忽略目录，`memory-bank/` 继续按用户要求保持 Git 忽略，且不修改用户控制的 `next.md`。
