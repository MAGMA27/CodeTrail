# 决策：工作区与项目概览优先于 Issue Agent

Status: proposed

## 问题

已实现系统提供受限 Python 索引、静态代码图和源码证据。用户明确需要提交本地路径或 GitHub 链接、随时浏览项目入口和主要功能、切换多个项目，并在项目图上定位 Issue 与潜在影响。原先直接进入 Issue Agent 的顺序缺少项目身份、来源管理与语义概览，目录聚合不能代表功能理解。

## 决定

产品顺序调整为工作区项目管理、本地/GitHub 导入、入口/功能概览、Issue Agent 和影响高亮。W1 的项目身份、持久化、索引归属和切换、O1 的规则入口/静态概览骨架以及 O2 的有证据功能语义生成已实现；O3 的默认概览持久化/历史浏览和 Issue 影响仍未实现，本记录保持 proposed；已完成索引与图工作台继续复用。首轮单用户、每个项目一个仓库、每次分析一个固定快照，多个项目独立切换。

Project 拥有来源与多个索引，导入任务管理获取状态及临时内容，Index 保存不可变源码，O1 ProjectOverview 提供入口/模块骨架，O2 FeatureGeneration 独立保存功能与符号映射及证据。语义关系标记生成方式和版本，不混入静态调用边。GitHub 首轮公开仓库；语言解析仍先验证 Python，多语言不是来源支持的隐含承诺。

本地注册校验服务端允许根目录；GitHub 获取固定 commit，受网络、路径、大小和时间限制，仓库内容不执行。失败不覆盖旧快照；概览与报告固定 index_id。既有 allow-list 查询规则在导入功能实施前保持有效，后续只通过受限注册层扩展来源。

## 替代方案

继续先实现 Issue Agent 可以较快演示定位，但不能满足无 Issue 的项目理解与多项目工作区。立即集成 CodeGraph/Archify 或独立图数据库缺少目标样本验证，不能直接解决功能语义归纳。先保留现有栈，采用有限实体/关系与证据映射，减少重写。

## 验收与证据

用户已确认产品需求。W1 已用两个服务端配置的临时仓库验证项目创建、索引隔离、源码证据隔离、失败不覆盖 latest 和应用重开恢复；O1 已用固定快照验证入口规则、无入口、静态路径、预算、项目隔离、HTTP/MCP 对照、证据引用和工作台联动；O2 已验证 fixture/real 适配、真实工具上下文、引用校验、预算/缓存/失败语义、HTTP/可选 MCP 和工作台证据钻取。GitHub 公网成功导入、O3 概览持久化及 Issue 影响分层仍待后续验收。全部范围覆盖后再将本记录标记 implemented。

## 后果

影响 API/服务、存储、契约与工作台；实施时更新其就近 README、子系统及 Schema。先完成项目身份与现有索引关联，保留历史 index_id；不自动迁移或删除用户数据。共享实施事实仍由子系统文档拥有，本地阶段计划保留在 memory-bank 并继续 Git 忽略。
