# 决策：Run 公开 SSE 事件流与断线续接

Status: implemented

## 问题

Run 的公开事件已经按连续 sequence 持久化，但工作台仍以短间隔轮询读取状态、事件和报告。轮询无法表达逐事件进度，也会在刷新、切换或网络短暂中断时增加重复读取和恢复边界。SSE 需要和既有 Run 事件表、HTTP 分页及 MCP 读取共享同一事实来源，不能增加只存在于进程内的第二事件日志。

约束是：事件流必须绑定 project/session/run 归属；游标不能跨 Run 或跳到未来；连接、批次、事件大小、空闲心跳和最长生命周期均有界；慢客户端不能积累无界内存或阻塞执行、取消和 health；仅发送公开事件，不发送隐藏思维链、密钥、完整私有 prompt 或原始模型响应。MCP 继续使用已有分页工具，不要求 SSE。

## 决定

增加只读端点：

`GET /api/projects/{project_id}/sessions/{session_id}/runs/{run_id}/events/stream`

端点在建立流之前完成 Run 归属和游标校验。初始游标可由 `after_sequence` 查询参数或 `Last-Event-ID` 请求头提供；两者同时存在时必须表示同一个 Run 和 sequence。SSE `id` 使用稳定的 `{run_id}:{sequence}` 格式，普通帧的 `event` 和 `data.type` 必须相同，`data` 复用已有公开 Event 契约。跨 Run、格式错误、负数或大于当前已持久化最大 sequence 的游标返回结构化 HTTP 错误，不建立流。

流建立后每次从 SQLite 读取 `sequence > cursor` 的有界页，先回放已持久化事件，再以短间隔重新查询同一事实来源追踪新增事件。每个批次读取和发送后推进游标；新增事件恰好落在回放与下一次查询之间时由下一次持久化查询补上，因此不依赖只存在于内存的发布器，也不会因断线丢失或重复事件。数据库连接只在单次读取期间持有，等待期间释放。发送终态事件后关闭流；若客户端从已完成的终态 sequence 续接，则发送一次非持久化 `run.stream.end` 控制帧后关闭，使客户端能识别完成而不无限重连。

进程内订阅管理器使用总连接数和单 Run 连接数上限，满载时在握手前返回 `budget_exceeded`/429。连接有最大生命周期和空闲心跳，批次、事件字节数和响应缓冲均有界；断开、取消和正常终止都释放订阅名额。到达生命周期上限只结束订阅，不改变 Run 状态，也不重新执行或取消 Run。

工作台先读取一次现有事件页建立当前历史，再用 SSE 订阅 `after_sequence` 之后的事件。以 Run/sequence 去重并拒绝跨流或跳号数据；断线以最后成功处理的 sequence 进行有限指数退避重连，握手成功本身不重置无进展重连预算，只有有效前进事件重置。切换 Project/Session/Run、刷新和卸载会关闭旧 EventSource，旧回调不能写入新范围。连接状态独立于 Run 状态；有限次连接失败后回退到既有有界轮询且不与 SSE 并行，四类终态控制帧或终态事件停止刷新。工具结果、报告、evidence、取消和 MCP 分页接口保持原样。

## 替代方案

- 继续 450ms 轮询：实现简单，但不能逐事件传递，也会持续重复读取；保留为 SSE 不可用时的明确有界回退。
- 进程内 publisher/队列：实时性更强，但重启或订阅建立竞态会丢失事件，还会产生第二事实来源；不采用。
- WebSocket：双向能力超出本步目标，连接和权限面更大；Run 事件是服务端到客户端的只读流，SSE 足够。
- 仅依赖浏览器 EventSource 的自动重连：无法控制重连游标、次数和切换时的旧连接；由工作台显式关闭并按最后成功 sequence 有界退避。

## 验收与证据

- API 流逐帧回放与既有 `/events` 列表完全一致；`id`、`event`、`data` 和 `run_id/sequence` 一致。
- `after_sequence`、`Last-Event-ID`、二者冲突、跨 Run、未知 Run、未来游标和容量满均有结构化边界结果。
- 活动 Run 能在持久化新事件后逐项收到；回放/追踪边界、断开后续接、终态游标、服务重启产生的 interrupted 事件和终态关闭均可验证。
- 连接断开释放名额；慢订阅不阻塞 health、取消和 Run worker；总连接/单 Run/批次/事件大小/心跳/生命周期均受限。
- 工作台展示连接状态与事件时间线，刷新、切换、卸载不重复启动 Run，不混入旧流；断线有限重连，SSE 不可用时回退轮询并在终态停止。
- 执行 `uv run --directory apps/api pytest -q`、Python 编译检查、`pnpm --dir apps/web test`、`pnpm web:typecheck`、`pnpm web:build`、`pnpm contracts:check`、`pnpm docs:check`，并完成本地 HTTP/浏览器证据记录。

本轮实际证据：后端完整测试 `118 passed`，Python `compileall` 通过；前端测试 `17 passed`、严格类型检查和生产构建通过；契约检查 `20 passed`，文档检查和本地 memory-bank 检查通过。`test_run_sse.py` 共 `12 passed`，其中 3 项为实际流场景；`run-event-stream.test.ts` 覆盖四类终态控制帧、错误终态、连续 open-error 上限、有效事件后预算重置、sequence 续接、去重/缺号和旧回调清理。本地 HTTP 使用 `curl --no-buffer` 从 sequence 10 逐帧收到 11、12、13，并正常结束；浏览器使用本地延迟假供应商以受限 SSE 生命周期触发断流，验证续接无遗漏/重复、终态报告/evidence、取消、Run 切换和刷新恢复。真实浏览器离线网络切换和真实 DeepSeek 语义质量仍未验证；`memory-bank` 未纳入 Git。

## P3-S1 验收修复

本轮将工作台订阅逻辑提取为 `apps/web/lib/run-event-stream.ts`，通过注入 EventSource 和计时器覆盖真实连接、错误、事件、终态和清理处理器。`run.stream.end` 的事件名与 Run status 分开校验，只接受 `succeeded`、`failed`、`cancelled`、`interrupted`，并要求当前 Run 与最后处理 sequence；连续 open-error 不再被 `onopen` 清零，只有有效前进事件重置五次重连预算，达到上限后关闭流并进入原有轮询回退。

服务端只收紧控制帧的终态契约和生成 Schema，SQLite 事件事实、Run 执行、HTTP/MCP 读取与取消语义不变。浏览器用本地假供应商和 `0.5s` SSE 生命周期制造中途断流，在新增事件期间重连，页面最终显示连续且不重复的事件；另验证了取消终态、Run 选择和刷新恢复。浏览器级操作系统离线切换未验证。

## 后果

SSE 仍是单向公开事件传输，不提供 Run 写入、取消或 MCP 流式接口；客户端必须保留最后成功处理的 sequence。连接容量是进程级而非跨多实例协调，适合当前本地单进程服务；未来若支持多实例，需要共享订阅协调或继续依赖持久化轮询。真实供应商的语义质量不因本步改变。
